# Сравнение кандидатов и устойчивость приоритета (PAN-57)

`analytics.priority_compare` — отдельная Python-диагностика. Она возвращает
JSON-совместимые словари, ничего не записывает и не меняет официальный score,
роли, основной pipeline или CSV. Экран и серверное подключение в этот PR не входят.

## Вход и вызов

Передавайте **всю таблицу узлов**, а не только пару или top-20: ранг и попадание
в top-K определяются относительно всех строк `pr`.

```python
from agent_tools import GraphStore, GraphTools
from analytics.priority_compare import compare, pair_stability

store = GraphStore.from_dir("out")  # после python -m money_graph --data data --out out
pr = store.nodes
a, b = "100000008165763100", "100000003684369100"

comparison = compare(pr, a, b)
stability = pair_stability(pr, a, b, top_k=20, spread=0.5, n_runs=1000, seed=0)
print(comparison["delta"], comparison["main_reasons"])
print(stability["a"], stability["b"], stability["a_above_b_frequency"])

# При необходимости — существующее сравнение связей и общих контрагентов.
links = GraphTools(store).compare_nodes([a, b])
```

`compare` принимает `nodes_roles.csv` как DataFrame или `GraphStore.nodes`.
Обязательны `gid`, `priority_score`, все шесть `contrib_*`, `boundary_factor`,
`role`, `role_score`, `depth`, `is_seed`, `in_kzt`, `out_kzt`, `in_deg`, `out_deg`,
`n_payers`, `n_receivers`, `n_seed_payers`, `n_seed_receivers`, `out_observable`,
`external_inflow_suspected`. Прочие поля карточки (`cluster_id`, `boundary`,
`in_tx`, `out_tx`) возвращаются, если присутствуют.

Для `pair_stability` нужны только `gid`, `priority_score`, `contrib_*` и
`boundary_factor`: можно передать результат `analytics.priority.run` напрямую.
Этот результат без ролей и признаков наблюдения недостаточен для `compare`.

Числа роли, потоков, контрагентов и связи с seed берутся из входной таблицы.
`GraphTools.compare_nodes` остаётся источником прямых связей и общих
плательщиков/получателей: здесь обходы графа не дублируются. Карточки используют
его общие поля и `node_warnings`; предупреждение о неполном входе дополнено
точными `in_kzt`/`out_kzt`. В результатах gid — строки, в том числе внутри
предупреждений. На входе принимаются целые числа или строки цифр; float
отклоняется, поскольку теряет точность 18-значных идентификаторов.

Одинаковые/неизвестные gid, дубликаты, недостающие колонки, пустая или неверная
диагностика дают `ValueError` с описанием проблемы. `top_k` и `n_runs` — целые
≥1, `seed` — целое ≥0, `spread` — конечное число в [0, 1]. При K больше числа
узлов все попадают в top-K; фактический размер указан в `effective_top_k`.

## Разложение и порядок

Весовая формула находится в `analytics.priority`; собственная модель здесь
не вводится. Веса: collect 0.25, остальные пять компонент по 0.15.

```text
score_from_contrib = boundary_factor × sum(contrib_*)
boundary_adjustment = (boundary_factor − 1) × sum(contrib_*)
rounding_residual = priority_score − score_from_contrib
priority_score = sum(contrib_*) + boundary_adjustment + rounding_residual
```

Каждый вклад и score опубликованы с независимым округлением до 4 знаков.
Поэтому допустимая абсолютная ошибка восстановления — **0.00035**:
6 × 0.00005 для вкладов плюс 0.00005 для итогового score (factor ≤1).
В текущих реальных данных максимум — 0.00020. Более сильное расхождение
считается ошибкой входа. Числа внутри результата не округляются повторно.

`a` и `b` сохраняют порядок аргументов. `rank` — место от 1 среди всех строк:
убывание **официального `priority_score`**, затем числовое возрастание gid.
Это тот же порядок, что в `top_nodes.csv`; `role_score` приоритет не определяет.

`delta` всегда означает **A − B**. Положительная разница вклада поддерживает A;
отрицательная поддерживает B. Отрицательная разница рангов означает, что A выше.
`main_reasons` — до трёх наибольших по модулю различий среди вкладов и поправки
границы; каждое содержит A, B, разницу и текст с числами. При равных модулях
порядок причин лексикографический по имени компоненты. Все остальные различия
остаются в `delta`. Поправка границы учитывается отдельно, поэтому её нельзя
ещё раз прибавлять к уже умноженным на factor вкладам. Разница factor сама по
себе не является добавкой к score.

`a_above_b` и `order_reason` отражают официальный порядок. При равных score
причина порядка — `gid_ascending`, даже если округлённые вклады различаются.
При нулевых различиях список числовых причин пуст.

## Эксперимент с весами

В каждом из `n_runs` сценариев независимо для шести весов берётся множитель
`U(1−spread, 1+spread)`. Весь граф получает один и тот же набор весов сценария.
Веса не нормируются; роли, признаки, нормировка компонент и boundary_factor
фиксированы. Общие хелперы извлечены из `weight_sensitivity`: восстановление
компонент `contrib_k / WEIGHTS[k]`, умножение на веса и factor, RNG и сортировка.
Численные результаты и контракт существующей `weight_sensitivity` сохранены.

При **точных исходных весах** используется опубликованный `priority_score`,
чтобы базовый сценарий воспроизводил официальный порядок, включая tie-break.
Это относится и ко всем сценариям при `spread=0`. В остальных сценариях,
как в существующей `weight_sensitivity`, ранжируются неокруглённые суммы из
опубликованных вкладов. Нет дополнительного округления, нормирования или
ограничения экспериментального score сверху единицей.

Это явная граница точности: из округлённых вкладов невозможно восстановить
неокруглённый официальный score. У почти равных узлов даже при очень малом
ненулевом spread порядок может меняться из-за округления входных вкладов.
Старая `weight_sensitivity` также использует восстановленную сумму для своего
базового top; её историческое поведение намеренно сохранено. Попарный результат
содержит отдельный официальный `baseline`.

| Поле | Как читать |
|---|---|
| `a/b.baseline_rank` | Официальное место при исходных весах |
| `a/b.rank_min`, `rank_max` | Лучшее и худшее место в проведённых сценариях |
| `a/b.top_k_count`, `top_k_frequency` | Число попаданий в top-K и доля от n_runs |
| `a_above_b_count`, `a_above_b_frequency` | Число сценариев, где A выше B, и доля |
| `parameters` | K, фактический K, spread, n_runs, RNG seed, версия NumPy и правило расчёта |
| `weights` | Исходные веса из `analytics.priority.WEIGHTS` |
| `data_version`, `source`, `n_nodes` | SHA-256 использованных колонок `pr`, их список и размер входа |

Базовый сценарий показан отдельно и **не добавляется** к `n_runs`. Равенство
экспериментальных score всегда разрешается по числовому gid, поэтому для
обратной пары частоты дополняют друг друга до 1.

Хеш строится из канонического JSON использованных колонок и строк, отсортированных
по gid. Он не зависит от исходного индекса, порядка строк или колонок. Хеши
`compare` и `pair_stability` различны: первая функция использует также роли,
потоки и границы наблюдения. Это версия входа диагностики, а не хеш сырых
Parquet-файлов; исходные файлы и `run_report.json` сохраняет вызывающий слой.
Все факты привязаны к `pr`, именам колонок, gid и этой версии.

## Ограничения и проверка

Устойчивость к весам **не является вероятностью вины, точностью модели,
подтверждением роли или доказательством правомерности проверки клиента**.
100% означает все проведённые сценарии, а не гарантию для любых весов.
Диапазон ранга — наблюдавшиеся минимум/максимум, не доверительный интервал.
Частоты относятся к выбранному распределению весов, а не к реальным исходам.

Эксперимент не меняет состав данных и не проверяет устойчивость к пропущенным
переводам, границе глубины 4, скрытому входу seed, порогу 5 000 KZT, дневной
точности дат или ошибкам определения ролей. Он не доказывает превосходство
сигнала над артефактом выгрузки. Нужна полная таблица: модуль не может обнаружить
строки, удалённые вызывающим слоем до вызова.

```bash
python -m pytest tests/test_priority_compare.py tests/test_priority.py -q
python -m pytest tests -q
python -m money_graph --data data --out out --check-repro
```

Тесты покрывают устойчивую и меняющую порядок синтетику, всю формулу с
поправкой границы и округлением, исходные веса и gid tie-break, неизменность
`weight_sensitivity`, перестановку строк, ошибки входа, совпадение фактов с
`compare_nodes` и оба реальных примера. Реальные тесты пропускаются только при
отсутствии архива `data/`; синтетика работает автономно.

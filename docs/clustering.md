# Кластеризация (PAN-35)

```bash
python -m analytics.clustering --data data --out out
```

Около 1,5 с. Пишет `out/clusters.csv` (строка на кластер) и `out/node_clusters.csv` (`gid, cluster_id, component_id` — для merge в `nodes_roles.csv`).

## Метод

1. **Слабосвязные компоненты.** Между компонентами денег нет, поэтому кластер никогда не пересекает компоненту.
2. **Малые компоненты (< 30 узлов) — один кластер целиком.** Узлы без рёбер (19 seed без переводов ≥ 5 000 KZT) — кластер из одного узла.
3. **Крупные компоненты — Louvain** (`resolution=1.0`, `seed=42`) на **неориентированной** проекции: вес пары = `sum_kzt(u→v) + sum_kzt(v→u)`. Направление при поиске сообществ не учитывается — это оговорка метода. Направление возвращается в сводке: входящие и исходящие хабы считаются по направленному графу.
4. **Устойчивость.** Разбиение повторяется ещё с 10 seed; `stability` — средний лучший Jaccard кластера с кластерами этих прогонов.

Выбор параметров: вес `sum_kzt` против `log1p(sum_kzt)` и невзвешенного — у `sum_kzt` выше модулярность (0,86 против 0,79) и устойчивость между seed (NMI 0,965 против 0,87).

## Результат на датасете

- 95 кластеров покрывают все 2 248 узлов, 19 из них — изолированные seed.
- 8 кластеров объединяют 2+ seed (в одном — 14 seed на 26 узлов).
- Медианная устойчивость 1,0; у 90% кластеров ≥ 0,8. Кластеры с устойчивостью < 0,6 помечены в `hypothesis`.

## Колонки clusters.csv

Обязательные: `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`.

| Колонка | Смысл |
|---|---|
| `cluster_id` | 1…K по убыванию внутреннего оборота |
| `sum_kzt_internal` | сумма рёбер, у которых оба конца в кластере |
| `top_gids` | до 5 gid с наибольшим внутренним оборотом (вход + выход), через `;` |
| `hypothesis` | до 3 графовых сигналов с числами, сформулированы как «признаки» |
| `component_id` | номер слабосвязной компоненты |
| `sum_kzt_in_external` / `sum_kzt_out_external` | поток из других кластеров / в другие кластеры |
| `hub_in_gid`, `hub_in_partners`, `hub_in_kzt` | узел с наибольшим числом разных плательщиков внутри кластера |
| `hub_out_gid`, `hub_out_partners`, `hub_out_kzt`, `hub_out_share` | узел с наибольшим числом разных получателей |
| `avg_edge_kzt` | средняя сумма внутренней связи |
| `transit_share` | доля не-seed узлов с `out/in` 0,8–1,2 |
| `truncated_share` | доля узлов на 4-м колене без исходящих (обрыв обхода) |
| `stability` | устойчивость кластера, 0–1 |

## Правила гипотезы

Сигналы в порядке важности:

| Сигнал | Условие |
|---|---|
| изолированный узел | нет внутренних связей |
| координирующий узел | один и тот же узел: ≥ 5 разных плательщиков и ≥ 10 разных получателей |
| консолидация | узел получает от ≥ 5 разных участников кластера |
| веерное распределение | узел отправляет ≥ 10 разным получателям |
| общая инфраструктура | в кластере ≥ 2 seed |
| крупные переводы | средняя связь ≥ 90-го перцентиля сумм связей по графу |
| транзитный контур | ≥ 20% не-seed узлов пропускают 80–120% полученного (seed исключены: их вход занижен) |
| граница обхода | ≥ 50% узлов на 4-м колене без исходящих |
| периферия | ни одно правило не сработало |

Пороги — константы в начале `analytics/clustering.py`.

## Окружение

Python 3.11 (как в Docker-образе `python:3.11-slim`), зависимости — `requirements.txt` в корне. `networkx` зафиксирован на 3.6.1: в 3.7 Louvain с другими seed даёт немного другие разбиения, и колонка `stability` меняется. На 3.11 и 3.13 с этой версией `clusters.csv` совпадает побайтово.

В пайплайн модуль подключается через `analytics.clustering.run(edges, nodes)` → `(node_clusters, clusters)`. Функция ничего не пишет на диск; запись делает CLI модуля или общий пайплайн `python -m money_graph` (через `money_graph/ranking.py`).

# Проверка версии и локальный пакет сдачи (PAN-68)

Скрипт создаёт материалы для приёмки PAN-49: отчёт команд, три кейса защиты,
четыре CSV и ZIP с SHA-256. Работает с зафиксированным commit в отдельном
временном снимке. Основной out/, рабочие файлы и ветки коллег не изменяются.

## Запуск

Нужны Python 3.11+ с requirements.txt, Git и Node/npm версии из README.
Frontend-зависимости устанавливаются через npm ci в отдельном временном
каталоге; для первого запуска может требоваться сеть. NVIDIA не используется.

После слияния выбранных PR возьмите нужный commit и из его корня выполните:

```bash
python scripts/prepare_submission.py --data /absolute/path/to/data --dest /absolute/path/to/new-submission
```

`--dest` должен быть новым каталогом **вне репозитория и каталога входных данных**.
Скрипт откажется перезаписывать существующий результат. `--ref` по умолчанию HEAD;
незакоммиченные файлы не входят в снимок. Версия самого скрипта должна совпадать
с выбранным commit. Число узлов для этого кейса по умолчанию 2248; для другого
набора его можно задать через `--expected-nodes`.

Проверки последовательно выполняются на одной копии исходных Parquet:

1. Полный `python -m pytest -q tests`, включая проверки реальных данных.
2. Основной pipeline с `--check-repro`; число узлов, лимит времени и SHA-256
   выходов дополнительно сверяются с run_report.json.
3. Пять контрольных вопросов через настоящий локальный orchestrator
   (`agent_orchestrator.orchestrator:answer_case`) и существующий verifier.
4. Выбор трёх отдельных примеров из новых CSV: первый rank, наиболее
   приоритетный transit, крупнейший видимый вход у depth=4. При равенствах
   используется точный числовой gid, а в JSON/Markdown он остаётся строкой.
5. `npm ci --ignore-scripts`, frontend tests и production build.
   `MONEY_GRAPH_TEST_OUT` указывает на свежие CSV снимка: проверка реальных
   выгрузок PAN-64 выполняется, а не пропускается из-за отсутствия переменной.

У каждого процесса лимит 600 с; в логе сохраняются команда, результат и время.
Любая ошибка/пропуск обязательного шага даёт ненулевой exit code, отчёт FAILED
и **не создаёт ZIP для сдачи**. Если подходящего кейса нет, это явно написано
в demo_cases.md; готовность всех трёх примеров также не считается пройденной.

## Результат

В `--dest/packet/` находятся:

- `acceptance_report.md/json`: commit, окружение, команды, PASS/FAIL и границы проверки;
- `demo_cases.md/json`: план показа, точные gid, значения полей CSV, исходная
  строка, evidence/priority_why, оговорки и следующий шаг;
- `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, `edge_table.csv`;
- `run_report.md/json`, логи тестов/build и evaluation с результатами вопросов;
- `manifest.json`, `SHA256SUMS`, `START_HERE.md`.

Только при успехе создаётся `submission-<commit>.zip`. ZIP строится по явному
списку файлов; исходные Parquet, .env, исходники, node_modules и сторонние
файлы в него не включаются. Отправка организаторам остаётся отдельным шагом.
В manifest есть SHA-256 трёх входных Parquet, чтобы воспроизвести именно этот
набор. Повторяемость подтверждается для CSV; ZIP и отчёты содержат время прогона.

Проверка целостности без повторного расчёта:

```bash
python scripts/prepare_submission.py --verify /absolute/path/to/submission-COMMIT.zip
```

Она сверяет перечень файлов, размеры и SHA-256 с manifest и SHA256SUMS.
Это контроль целостности, а не цифровая подпись или новое выполнение тестов.

## Что остаётся для PAN-49

Этот отчёт не объявляет выполненными Docker/browser smoke, живой NVIDIA API,
ручной хронометраж выступления или проверку более поздних коммитов. Эти пункты
явно перечислены в отчёте. Docker/browser проверяется отдельным существующим
`scripts/docker-smoke.sh` из PAN-66. После новых слияний сформируйте новый
пакет, чтобы результаты, роли и демонстрационные примеры относились к одной версии.

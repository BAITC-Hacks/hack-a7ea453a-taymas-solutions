# Evidence verifier и evaluation AML-вопросов (PAN-47)

Задача модуля — гарантировать, что ответ AI-ассистента не содержит выдуманных сумм, ролей и связей. LLM (PAN-46) формулирует ответ, верификатор сверяет каждый факт с выгрузками, и в UI как факт попадает только то, что подтверждено CSV.

```bash
python -m agent_tools.evaluation --out out                   # 5 контрольных вопросов, pass/fail
python -m agent_tools.evaluation --out out --show            # + ответы целиком
python -m agent_tools.evaluation --out out --report out/agent_eval.md
```

## Контракт ответа агента

Оркестратор возвращает не свободный текст, а структуру ([agent_tools/answer.py](../agent_tools/answer.py), `ANSWER_SCHEMA`). Каждое число или роль, которые ответ утверждает, оформляется как `claim` со ссылкой на источник.

```json
{
  "question": "Кто собирает деньги с этих gid: …?",
  "intent": "common_collector",
  "provider": "fallback",
  "status": "ok",
  "summary": "Признаки общего сборщика у 100000004015047100: … напрямую 544 884 KZT за 11 перев. … Гипотеза для проверки.",
  "gids": [100000001616816100, 100000004015047100],
  "claims": [
    {"kind": "node", "gid": 100000004015047100, "field": "role", "value": "consolidator",
     "source": {"file": "nodes_roles.csv", "gid": 100000004015047100, "column": "role"}},
    {"kind": "edge", "src": 100000001616816100, "dst": 100000004015047100, "field": "sum_kzt", "value": 110500.0,
     "source": {"file": "edge_table.csv", "src": 100000001616816100, "dst": 100000004015047100, "column": "sum_kzt"}},
    {"kind": "hypothesis", "text": "гипотеза: деньги консолидируются для дальнейшей переброски"},
    {"kind": "not_observed", "text": "не наблюдается в данных: исходящие переводы после 4-го колена"}
  ],
  "tool_calls": [{"tool": "find_common_collectors", "args": {"gids": ["100000001616816100", "…"]}}],
  "warnings": [{"code": "seed_inflow_underestimated", "gid": 100000001616816100, "message": "…"}],
  "next_steps": ["сравнить поступления 100000004015047100 от каждого из заданных gid по датам"]
}
```

Помощники `node_claim`, `edge_claim` и `cluster_claim` из `agent_tools.answer` собирают claim вместе с правильной ссылкой на источник. `warnings` копируются из результатов инструментов.

## Что проверяет `verify(answer, tools)`

| Проверка | Код ошибки |
|---|---|
| ответ соответствует `ANSWER_SCHEMA` | `schema` |
| каждый gid (в полях, claims и **в тексте**) есть в `nodes_roles.csv`; gid из текста перечислен в `gids` | `unknown_gid`, `gid_not_listed` |
| claim узла, ребра или кластера совпадает с CSV (суммы ±0.01 KZT, скоры ±1e-6, строки точно) | `value_mismatch` |
| ребро или кластер существует, колонка есть в файле | `unknown_edge`, `unknown_cluster`, `unknown_field` |
| `source` указывает ровно на тот же файл, gid или ребро и колонку, что и claim | `bad_source`, `missing_source` |
| каждое число в `summary` и `next_steps` прослеживается до данных (см. ниже) | `untraced_number` |
| узел 4-го колена не назван terminal | `depth4_terminal` |
| узел 4-го колена сопровождается предупреждением о границе обхода | `missing_boundary_warning` |
| в ответе есть gid и хотя бы один подтверждённый факт | `no_gids`, `no_verified_source` |
| `tool_calls` — только из allow-list, аргументы проходят схему | `tool_not_allowed`, `invalid_tool_args` |
| нет обвинительных формулировок («организатор», «преступник», «виновен»…) | `accusatory_language` |
| вывод помечен как гипотеза («гипотеза», «признак», «кандидат»…) | `missing_hedge`, `unmarked_hypothesis` |
| в ответ не «всплыли» инструкции из данных | `instruction_echo` |

**Числа в тексте.** Верификатор разбирает числа с учётом формата вывода: «3 848 436», «3.8 млн», «110 тыс.», «15%». Каждое число должно совпасть, с точностью до показанного разряда, с одним из значений:
- claims ответа;
- строки использованных узлов, их рёбер и кластеров;
- тексты `evidence` / `priority_why` / `hypothesis`;
- результаты `tool_calls`, повторно выполненных верификатором.

gid и даты из этой проверки исключены.

> Ограничение: небольшие целые числа (1–10) почти всегда встречаются где-то в данных, поэтому по тексту такую подделку не поймать. Количества надёжно проверяются только через claims: `node_claim(gid, "n_payers", 3)` сверяется с конкретной колонкой конкретного gid. Оркестратор должен оформлять каждое утверждаемое количество как claim.

**`mark_unverified(answer, report)`** возвращает копию ответа, в которой неподтверждённое не выдаётся за факт:
- claim с расхождением или без данных превращается в `{"kind": "not_observed", "text": "не наблюдается в данных: …"}`;
- claim без источника или с неверной ссылкой превращается в `{"kind": "hypothesis", "text": "гипотеза (нет подтверждённого источника): …"}`.

## Защита от prompt injection через данные

Тексты `evidence`, `why` и `hypothesis` — это данные, и в них может оказаться «ignore previous instructions». Три уровня защиты:
1. **Промпт** ([agent_tools/safety.py](../agent_tools/safety.py)). Оркестратор передаёт результаты инструментов только через `data_block(result, label)`: одна JSON-строка между маркерами `<<DATA …>>` и `<<END DATA>>`. Переводы строк экранированы, маркеры внутри значений обезврежены, размер ограничен. Строка `DATA_POLICY` идёт в system prompt.
2. **Вызовы.** `call_tool` выполняет только инструменты из allow-list, а лишние аргументы отклоняет по JSON-схеме.
3. **Ответ.** Верификатор отклоняет `tool_calls` вне allow-list и текст с признаками инструкций (`find_injection`).

## Evaluation-набор

Пять кейсов строит `build_cases(tools)` по правилам, **без захардкоженных gid**, поэтому набор работает на любом прогоне пайплайна:

| Кейс | Вопрос | Как выбран gid | Что обязан содержать ответ |
|---|---|---|---|
| `priority` | Кого проверить первым и почему? | первый в `top_nodes.csv` | gid, его `priority_score` и роль |
| `common_collector` | Кто собирает деньги с этих gid? | узел с наибольшим числом seed-плательщиков, вопрос задаётся про этих seed | сборщик, его роль, сумма прямого перевода |
| `trace` | Откуда пришли деньги и куда ушли? | не-seed узел с наибольшим приоритетом, у которого видны и вход, и выход | крупнейший плательщик и получатель с суммами |
| `depth4` | Является ли узел конечным получателем? | узел 4-го колена с наибольшим входом | предупреждение `depth4_outflow_unobserved`, роль не terminal |
| `empty` | Кто общий сборщик для двух узлов? | два узла без исходящих | `status: "empty"`, без выдуманного сборщика |

`run_eval(answer_fn, tools)` прогоняет ответчик по кейсам. Кейс засчитывается, если ответ прошёл верификатор **и** ожидания кейса. Ответчик — функция `answer_fn(case, tools) -> answer`:
- `template_answer` — эталон без LLM: собирает ответ прямо из результатов инструментов. Это нижняя планка качества;
- оркестратор PAN-46 подключается так же, для режимов fallback и NVIDIA: `--answerer пакет.модуль:функция`.

Если ответчик падает (timeout, quota, ошибка API), кейс засчитывается как FAIL с причиной, а прогон продолжается.

Результат на реальных данных (эталонный ответчик): **5/5**. Все 17 утверждений в пяти ответах вручную сверены с CSV.
